# GPU 驱动的 XPR 绘制（设计，2026-10-04 起）

目标：XPR 绘制（1-1 每帧约 5400 次）在渲染线程上只剩"绑管线（换材质时）+ 推 user data + 一次间接绘制"，
把 XPR 现在每次约 1.5 µs（每帧 7.7 ms，诊断计时下 10 ms）的 CPU 成本降到约 0.1–0.2 µs。10-03 的不安全上限实验：
native 路径绘制全部免费时帧率 +60%。

## 1. 现状（10-04 夜测，1-1 站立）

- 每次 XPR 尝试约 4900 周期：找记录 17%、状态/目标检查 20%、gather（读 guest 字并比较）23%、资源证明 11%、
  发射（上传展平数据、查参数/索引缓冲、目标转换、绑定、绘制）29%；命中约 85%。
- 干净串（只有 user data 变化的连续 XPR 绘制）很短：大多 1–8 个，打断的是着色器地址（换材质）。逐串分批并行
  的并行度不够，所以走 GPU 驱动。
- 10-03 的 table mode 试点（scratchpad table-mode-v2/v3 补丁、table-xpr-v3.inc，能干净地应用到当前代码）：
  翻译器已能让缓冲经 BDA 页表按运行时 V# 读取；SRT 槽位若也经 BDA 读，游戏每帧改写的页（逐 pass 常量）
  在页保护下同步次数涨 4 倍，于是退回 CPU 逐次求值槽位，每次绘制仍约 1 µs（槽位 0.14、缓冲证明 0.15、
  参数/索引查找 0.15、目标 0.10、发射 0.07，外加约 0.4 µs 的 PM4 处理）。

## 2. 核心判断

每帧每个对象只有约 2.4 个字会变，但分散在成千上万个页里：页保护追踪（每次异常 + 重新保护数微秒）和逐次
拷贝（每次绘制的 CPU 工作）都把成本留在 CPU 上。唯一能让每次绘制的 CPU 工作趋近于零的是 PS5 自己的模型：
CPU 与 GPU 共享内存——GPU 直接读 guest 的主机内存。

## 3. 架构

1. 内存（统一内存模型）
   - guest 直接内存是页面文件支持的文件映射，主机上有一个连续视图。用 VK_EXT_external_memory_host（5090：
     导入对齐 4 KiB）把它导入为一个或几个 VkDeviceMemory/VkBuffer，得到设备地址 `import_base + 后备偏移`。
   - BDA 页表（已有，guest 页 -> 设备地址）对"CPU 写、GPU 读"的页指向导入内存（零拷贝、不追踪写），
     对 GPU 写的缓冲（渲染目标、计算输出）和大块静态数据（几何）仍指向缓冲缓存的显存副本。
   - 风险：NVIDIA 能否导入文件映射视图；GPU 经 PCIe 读系统内存的延迟（SRT 是 3–4 级依赖链）。先做实验。
2. 翻译器（GPU 驱动模式，扩展 table mode）
   - SRT 读取（标量加载）经页表直接读 guest 内存，不再由 CPU 展平。
   - 缓冲：运行时 V# -> BDA（table mode 已实现），含越界。
   - 图像/采样器：运行时 T#/S# -> GPU 侧哈希表 -> bindless 下标（描述符索引：运行时数组、update-after-bind、
     部分绑定，5090 全支持，采样图像上限 104 万）。
3. 运行时
   - 每次绘制：推 user data（几何根等）、`vkCmdDrawIndexedIndirect`（参数在 GPU 上）；索引池一次绑定、
     firstIndex 由地址算出。
   - 每串（换管线/状态时）：管线、渲染目标、动态状态，沿用 native 路径的状态捕获。
   - 每帧/每次提交：bindless 表与 T# 哈希表维护（纹理缓存登记的图像）、CPU 改写过的纹理在提交点刷新、
     只读纹理固定布局。
   - 回退：着色器对翻译不了、T# 未登记（GPU 写反馈，下一帧补登记）、采样图像同时是渲染目标等 -> 普通/native 路径。
4. 验证：同一绘制两路求值对照（资源与常量）、逐像素截图对照、长时间游玩。

## 3.1 实验结果（10-04 夜，src/local/host-import-probe.h，KYTY_HOST_IMPORT_PROBE=1/2）

- E1 导入：直接内存视图 base 0xfc00000000、13.5 GiB。HostAllocation 类型可导入（内存类型 2/3，
  HostVisible|HostCoherent，堆 1），64 MiB–2 GiB 都成功并有设备地址，4 GiB 失败（单次上限 < 4 GiB）；
  导入约 9 GB/s（锁页），所以按需分块导入（例如 256 MiB 一块），不锁全部 13.5 GiB。HostMappedForeign 不支持。
- E2 延迟：5400 个"绘制"（4 级依赖读 + 64 字，表全不相同 = 最坏情况）。一次派发：系统内存 ~470 µs、显存
  ~10 µs；每次绘制一次派发：系统内存 1.3–2.1 ms、显存 ~0.45 ms。即逐次绘制每次多 ~0.15–0.3 µs GPU 时间，
  5400 次 ~1–1.6 ms（实际 78% 的表帧内共享，会命中 L2）。1-1 GPU ~11.6 ms，可接受；若 GPU 成为瓶颈，
  改为提交点把热点页从导入内存 GPU 侧拷进显存镜像。

## 3.2 第一阶段的具体形态（10-04 夜定）

先做"混合"版，所有 XPR 对（含带纹理的）都走它；T#/S# 仍由 CPU 按计划求值，以后再挪到 GPU：

- 内存：直接内存视图按 256 MiB 块在映射时导入；BDA 页表里"已映射、没有登记缓冲"的页写入导入地址并在
  bit 0 打标记（原有 BDA 着色器把带标记的项当缺页，行为不变；GPU 驱动着色器去掉标记直接读）。登记/注销/
  映射/解除映射时按流顺序改写页表项。显存缓冲仍是 GPU 写入数据和静态几何的家。
- 翻译器（table mode v4，VS 与 PS）：SRT 槽位在函数入口经页表由 GPU 读（只读需要的槽位及其地址依赖）；
  缓冲经运行时 V# 走 BDA；图像/采样器仍是普通绑定，它们的 T#/S# 字由计划给出，CPU 每次绘制求值。
- 运行时：每次绘制 CPU 只求值图像相关槽位 -> 图像集缓存（按 T#/S# 字，持有描述符集：图像、采样器、页表、
  故障缓冲；每帧首次使用时校验图像仍然有效）-> 绑定（材质变化时）-> 推 user data（含 LOD 统计字）-> 间接绘制。
  已登记显存缓冲的 CPU 改动用 BDA 脏区域位图在每串开头整体同步（与 BDA 计算着色器相同）；参数/索引缓冲
  按地址缓存查找结果。
- 时序语义：系统内存的读取发生在 GPU 执行时（游戏若在 GPU 真正读之前改写会读到新值）。由于每帧剔除结果
  的回读把游戏 CPU 卡在 GPU 之后，环形缓冲 >= 2 帧即安全；用校验模式（CPU 在翻译时求值同样的槽位，GPU
  比较并计数不一致）实测。

## 3.3 第一阶段实现记录（10-04 夜）

- 导入：`GuestMemoryImport`（cache/guestMemoryImport.*），按 256 MiB 块在映射时导入；1-1 加载导入 42 块、共约 3 s。
- 页表：第一次试做"未登记页在主页表里写带标记的导入地址"，结果原有 BDA 着色器的 SPIR-V 变了（多了标记判断），
  静态预编译与驱动缓存全部失效，计算管线同步编译 160 s、300 s 内到不了 HUD。改为主页表之后的两级导入表
  （第一级每 64 MiB 一项，块 4096 项），只有表模式着色器读：先主表（登记缓冲 = 显存），再导入表（系统内存）。
  原有着色器逐字节不变。
- 一次大的 GPU 映射（无直接内存后备的区段）曾把导入表块用完：改为按"有后备的映射片段"写项、只为有后备的
  窗口分配块（`GetBackedPieces`）。
- 特化：表模式程序用正常路径特化的可移植形式（`PortableFormats`、去掉 byte_base_offset）；缓冲的步长、格式、
  dst_sel 都由 GPU 从读到的 V# 现算（与 `BufferDescriptorWord` 相同的缓冲字），所以一个程序适用于任何缓冲。
  图像特化由 CPU 保证：新图像集经正常路径的 SRT 求值（`GetGraphicsPrograms(table)`），选不到同一表模式程序就拒绝
  （拒绝结果缓存 300 帧）。
- 游戏经常登记着色器（`ShaderMapGeneration` 每帧在动）：起初按代数清空全部对，导致每帧约 200 次重新存储、
  53 个新图像集、29 fps；改为按对比较地址处代码哈希（`ShaderHashAt`）。
- 图像集键里的 T# 带 LOD 统计字段（游戏每帧重新分配计数器）：每帧约 100 个新图像集；键里屏蔽这些字段
  （与 native 记录相同），LOD 统计字每次绘制由 CPU 算出推送 -> 每帧 0.2 个。
- 同进程 A/B（1-1 站立，tab2）：表模式 44.4 fps / native 44.2；渲染线程表模式少约 1.3 ms，但 GPU 忙
  18.6 ms 对 14.4 ms（+4.3 ms），渲染线程忙 88%：GPU 成了瓶颈。区域同步每帧 +950（全局脏区同步）。
- 让 SRT 槽位页也经故障登记成显存缓冲（tab3）：两条路径都变慢（native 28.5 fps，记录命中掉到 800/帧，
  上传与写故障增加）——与 10-03 试点结论相同，撤回。保留：缓冲读按 V# 范围在入口一次翻译（连续则直接
  寻址），范围无缓冲时一次性为其全部页记录故障（合成一个缓冲）。
- 竞争实测（KYTY_TABLE_XPR=3：每 64 次绘制记录着色器原地读的槽位值，GPU 完成后 CPU 再读一遍）：每帧验证
  约 5000 个槽位，377 个（7.6%）在翻译之后、GPU 完成之前被改写。即游戏会在 GPU 仍在读时改写部分 SRT 数据
  （急切标签让它跑在我们的 GPU 前面），原地读不能保证正确——这一路线的前提不成立。
- 另一个事实：native 记录的展平 SRT 也在系统内存（KYTY_STREAM_UPLOAD 环），GPU 读它只有一级延迟；表模式
  多出的 GPU 时间来自多级依赖读与逐槽位页表翻译，而不是系统内存本身。
- 竞争的根因（排除 GPU 写的页后每帧仍约 419 个变化）：游戏在命令缓冲里用 CP DMA 在两次绘制之间改写每个
  pass 的常量（0x208883000 一页的矩阵），模拟器在翻译时就用 CPU memcpy 完成这些拷贝（`BufferCache::CopyBuffer`
  两侧都不是 GPU 写时）。翻译早、执行晚的绘制原地读到的是后面 pass 的值——原地读在现有 CP 模型下不正确；
  另有少量下一帧才改写的页。

## 3.4 第一阶段 v5（10-04 夜改）：翻译时快照

- 翻译器：着色器读的槽位全部来自一个"块"（逐槽位 dword），块后接每个缓冲的设备地址与 dword 长度；块的设备
  地址作为两个 shader data dword 推送。着色器里没有页表、没有导入、没有依赖链：一级读，与 native 的展平 SRT 一样。
- 运行时：每次绘制按计划求值所有需要的槽位（翻译时快照，正确性与正常路径/记录相同）、T#/S# 选图像集、
  V# 经缓存（按 V# 字，证明：登记代数 + 区域 CPU 代数 + 图像起点代数）解析为缓冲设备地址，块写入专用的
  可取设备地址的上传环（BufferCache::GetTableUploadBuffer），推送用户数据 + LOD 统计 + 块地址。
- 去掉：直接内存导入（及其约 30 GB 锁页工作集）、导入表、表模式的全局 BDA 脏区同步、竞争校验模式。
- 补：标量缓冲读（s_buffer_load，`ReadConstBuffer`）也走块里的设备地址（`LoadWordInBounds`），否则这类着色器
  （例如贴花的模板标记 VS 33a379cd）翻译失败、整对退回 native。

实测（v5c，1-1 站立，同进程两轮）：native 44.9/45.4 fps，表模式 45.5/45.8，表模式+续接 45.7/46.2；GPU 忙
14.35 -> 15.0 ms（v4 是 +4.3 ms）；截图一致。表路径每次 TableDraw 约 1.4 µs，与 native 记录持平：槽位 0.43、
图像集 0.15、缓冲 0.56、发射 0.25 µs（census，3760 次/帧）。渲染线程采样（表模式 2）：TableDraw 含被调约 29%
（约 6 ms/帧），其中自身 45%（槽位链上等冷的 guest 行约 12%、`unordered_map` 解析缓存的桶/节点未命中约 14%、
区域代数循环约 4%）、guest 读的 memcpy 约 14%、缓冲解析未命中路径约 19%（ObtainBuffer 12%、HasImageStartingAt、
EnsureBufferContents、ClampRangeSize）、图像集逐帧校验 5%、Transit 3%。同一采样里计算派发约 29%（6.1 ms/帧，
其中 MaterializeResources 约 2 ms）、普通绘制约 3.6 ms。录制线程每帧约 17–19 ms：渲染线程再快 2–3 ms 它就成了瓶颈。

Latria（world-latria，v5h）：native 46.1/45.2 -> 表模式 53.0/53.1（+16%），截图一致；表模式下渲染线程每帧

（CX_IND + UC_IND + SH_IND 三个间接寄存器块），其余是 `SH[0x8c+3] (SH[0xc+2]) (INDEX_BASE IBSIZE) | DRAW`。
录制线程（Kyty.Record）约 80% 在驱动里；渲染线程有时在 pushConstants 里等录制环（G-buffer 阶段突发）。

## 3.6 计算派发的表模式（10-05 凌晨，KYTY_TABLE_DISPATCH）

- 依据：1-1 每帧约 1220 次异步派发（剔除链，平均 4.7 µs/次，带原子缓冲的 625 次、400 个着色器 4.07 ms）和
  约 800 次图形队列派发；普通路径的 program 阶段（MaterializeResources：读冷的 SRT + 特化 + 程序查找）每次约
  1.8 µs，rebind/find/bda/commit 再约 1.3 µs。
- 实现：翻译器允许写/原子缓冲（物理指针的存储与原子，u64 原子按 qword 长度）；GetComputeProgram(table) +
  异步计算管线（原生绑定布局，可绑定缓存的描述符集）；TableDispatch 与绘制共用 TableEvaluate/TableSet/
  TableBlocks；写缓冲每次按写入取得（ObtainBuffer(written)，与普通路径一样记录 GPU 写入）；普通路径的特殊派发
  （线性拷贝、清除）用过的着色器、线程维度派发、帧捕获/帧生成不走表路径；计算链与屏障照搬 DispatchDirect。
- 第一次 A/B：CPU 异步派发 5.74 -> 3.73 ms/帧，但 GPU 忙 +1.2 ms、渲染线程空闲 +3.7 ms（剔除链在关键路径上），
  帧率 46.9 -> 43.3。逐着色器 GPU 计时（tracem + marks-diff.py）找到原因：
  1. 表模式程序用 IR::PortableFormats（运行时格式解码），而普通路径的 warmup 让下次启动编译精确特化（静态格式
     解码）；表模式还在入口用 128 路 switch 从 V# 现算缓冲字。改为：块里每个缓冲 5 个 dword（地址、长度、
     CPU 算好的缓冲字和步长），表模式程序用精确特化，每次使用由 CPU 校验 V# 的格式/dst_sel（不一致的缓冲置入
     TablePair::portable，重新编译时只有它运行时解码）。表模式绘制的 GPU 也因此少了约 0.5–0.7 ms。
  2. 写冲突屏障按 HasShaderBufferWrites 的判断（非空 V#）；CPU 改过的小范围按 ObtainBuffer 的做法从上传环读
     （不上传进缓冲、不重新加保护），屏障/拷贝不再多出。
- 结果：GPU 忙 14.24 vs 14.10 ms（持平），1-1 两轮 46.7/46.4 -> 47.6/47.6（+2.2%，仅计算派发）。

## 3.7 全部表路径（10-05 凌晨）

- 同进程 A/B（XPR 表绘制 + 计算派发表模式，一起开关）：1-1 45.0/45.3 -> 49.6/49.8（+10%），Latria 45.5/45.7 ->
  53.8/52.1（+16%）；GPU 忙比 native 少约 0.6 ms；截图一致。
- 表模式程序改为编译工作线程翻译（ProgramCache 里的 TableJob：代码、user data、输入信息的副本；下次查询时
  在锁内发布）。同步翻译时第一次世界巡检的 1-1 有 37 次、合计 13.7 s 的卡顿（A/B 预热 150 s 没暴露）。
  翻译中 PipelineCache::TablePending()：TableStore/TableResolveSet/TableDispatch 下次再试，不当作拒绝。
- 图像集按普通路径 CommitBindings 的布局：绘制状态的目标图像用其附件布局与访问（NativeXprEmitTargets 负责
  转换，集合记录目标身份，状态变了就退回）；每次绘制都核对集合图像的布局（别的工作可能移动过），放在
  TransitGroup 里。
- 写图像的着色器不走表模式：计算派发的存储图像（每帧约 86 次）走表路径时剔除链变慢（1-1 +10% 掉到 +4%，
  渲染线程空闲 1.6 -> 2.5 ms，原因未细查）；贴花（PS 读写 G-buffer、采样作为附件的深度）需要普通路径的目标与
  反馈环处理。

## 3.8 预热与存储请求（10-05 凌晨）

- 世界巡检（HUD 后 20 s 开测）：开表模式时 1-1 前半分钟只有约 30 fps（不开时 45），稳态 46 fps。原因：每个对在
  程序/管线编好之前每帧发一次存储请求，那次绘制走普通路径（约 3.6 µs + TableStore），几百个对一起预热时每帧
  多出几百次普通路径绘制；稳态里也有约 150 次/帧：同一着色器对在不同目标格式下像素程序的导出特化不同
  （"another specialization"），TableStore 什么都不记，下一帧又请求。
- 改：表存储请求每帧预算（KYTY_TABLE_STORE_BUDGET，默认 32；超出的绘制用原生记录）；另一特化的绘制状态记为
  拒绝的变体，之后直接走原生。
- 待做：程序按绘制状态（变体）而不是按对持有，让同一对在不同目标格式下都能走表路径（集合也要按程序的布局分开）。

## 3.9 Stonefang 的设备丢失（10-05 凌晨）

- 世界巡检里 2-3 和 Stonefang 在转视角时 VK_ERROR_DEVICE_LOST（之后 BPE 任务线程在 eboot+0xa2e820 读到垃圾句柄）；
  Stonefang 存档一轮行走+转身必现。只开计算派发表模式也复现，只在这些运行里出现的表模式计算着色器有 4 个，
  其中 3 个（粒子模拟，7 个写缓冲）用 FLAT_LOAD 经 64 位指针读全局内存。
- 根因：普通路径对用到平坦/全局内存的程序每次都 PrepareBdaBindings（按读取计划把指针读到的范围在 BDA 页表里
  准备好、同步 CPU 改过的区域，并让提交后处理着色器的缺页），表路径没有这一步，读到旧页 -> 模拟结果错 -> 游戏
  读回的句柄、间接参数都是垃圾。先拒绝这类程序验证了根因（6 轮无事），但 1-1 有 106 个计算着色器用全局内存，
  表模式派发从约 1270 掉到约 790 次/帧；改为 TablePrepareBda：用块里的槽位和 user data 求读取计划，
  PrepareBdaReadRanges（无界时 PrepareBda），TablePlan::global_memory 标记这类程序。
- 同时：u64 原子的指针按绝对地址向下对齐到 8（与普通路径绑定偏移的效果相同，基址 4 mod 8 时不再错位）；表绘制的
  着色器写缓冲时与普通路径一样结束渲染并加 ShaderWriteBarrier（之前漏了）。
- 验证：Stonefang 6 轮行走+转身无事；1-1 同进程（预热 90 s）native 44.9/45.1/45.3 -> 表模式 49.9/49.5/50.4
  （+10.7%）；去掉屏障或去掉 BDA 准备都在噪声内（49.8/50.0），两者保留。预热 40 s 时第一轮还在补存储，
  表模式 40.6、native 31.4（native 记录在表模式期间没被用到，要重新存），A/B 至少预热 90 s。
- 也试了：连续同一集合、同一绘制状态的表绘制跳过目标与集合图像的转换检查（图像状态/CPU 脏/分辨率/元数据
  纪元都没变时）：emit 阶段每帧只少 0.07 ms，帧率在噪声内，已删除。存储预算后 1-1 稳态 table_store_variant
  130 -> 17 次/帧、table_stores 16 -> 2 次/帧。

## 3.10 载入后的预热、贴花、写缓冲（10-05 清晨）

- 世界巡检（wt3）：表模式载入后约一分钟比 native 慢得多（1-1 HUD 后 20 s 站立 30 fps，native 45）。原因：表模式程序
  的翻译、表模式管线、native 记录的管线、优化重编译全挤在同一个 2 线程 FIFO 编译队列里，几百个表模式翻译排在前面，
  native 记录的管线一直等着（xpr_store_pending ~250/帧），绘制全走普通路径。改：
  1. 表模式的程序与管线用自己的编译线程池（TableWorkers，后台优先级，线程数同着色器预取：硬件线程的一半）。
  2. 存储请求等的翻译或管线没编完时，对子持有它的完成标志（PipelineCache::TableWaiting / PipelineWaiting），
     编完前不再请求存储（以前每帧都请求，前 32 个等待中的对占满预算，其余的对排队，预热串行化）。
  结果（1-1，HUD 后每 10 s）：改前 40.8/42.4/42.7/42.4/43.6/51.1/53.7，改 1 后 43.3/44.0/44.7/44.9/47.5/50.4/52.2
  （预热期间不再低于 native，表绘制 2266 起步而不是 297）。
- 贴花进表模式：像素着色器允许存储图像（EnterTableMode）；TableResolveSet 按 CommitBindings 的规则给布局：同一图像
  既采样又存储（force_general，贴花的 G-buffer 4 层 R32_UINT 数组）整张 General，存储图像 General，深度目标按目标
  的附件布局（贴花采样附着中的深度）；每次使用检查存储图像 SafeToDownload（GPU 修改、无 CPU 脏、无缓冲写入，否则
  普通路径重新获取）；线性存储图像不进集合（回读登记）。1-1 表绘制 8430 -> 9050 次/帧。
- 写缓冲缓存（按 V# 记住 owner，范围仍归 GPU 时跳过 ObtainBuffer 的查找）：同进程 A/B 关掉它反而略快（49.7/50.3 vs
  49.4/49.7），已删除。
- 稳态：1-1 53.3–53.7 fps（native 45.1，之前表模式 49.9）。同进程 A/B（预热 90 s）native 45.0/44.2/45.1 -> 表模式
  51.9/53.7/54.4（+19%）；只关贴花 45.9/45.8（贴花约 +3.7 fps）。
- 截图对比发现表模式少了 1-1 地面的石板（关掉贴花也少）：表模式的对只按 VS/PS 地址区分，而顶点程序按
  START_INST_LOC（间接绘制把起始实例写进的 GS user SGPR，3b351932）分别翻译，native 记录的键里有它，对的键和
  绘制状态键里没有：同一对的直接绘制（-1）和间接绘制（GS_2）共用了一套程序，按那个 SGPR 取每物体数据的着色器读到
  旧值。改：对的键加上 start_instance_user_sgpr，TableContinue 也要相同。
- 世界巡检里 Shrine 复活后崩溃：RebindImages "do not settle"（同一绑定里互为别名的视图互相把对方的图像挤掉，
  原有问题，捕获时也见过）：过半轮次后仍不稳定的图像绑定为空图像，不再退出。

## 3.11 走动时（10-05 清晨）

- 1-1 HUD 后 20 s 的世界巡检：站立 52.6、转身 56.6，走动 42.5（10-04 native 45.8，那时还没有 start instance 修正，
  它本身 -1.5~2.5%）。走动时的 census（scratchpad walk-census.ps1，站立/走动各一次）：渲染线程 +3.3 ms/帧，其中
  解析 V# 0.30 -> 1.28 ms（1076 -> 3791 次/帧）、普通路径 async 派发 +1.1 ms、普通绘制 +1.2 ms、programs +0.5 ms
  （后几项是新内容，native 一样要付）。
- 解析多的原因：解析缓存的有效性用一个全局代（缓冲注册纪元、图像起点纪元、映射纪元），走动时每帧约 13 次缓冲注册，
  每次都让全部条目失效。改为每个条目记住它最后被证明时的注册纪元，全局纪元变了就只看它的跟踪区（4 MiB）的注册
  戳（BufferCache::RegionRegistrationEpoch），旧于它就继续有效；只有需要图像起点（格式化缓冲）或映射（被截断、
  未映射）的条目才跟一个特殊代。走动解析 3791 -> 2164/2430 次（1.28 -> 0.89/0.99 ms），站立 1076 -> 891/945。

## 3.12 帧链与 GPU（10-05 清晨）

- 稳态（不来回切换模式）1-1：native 45.1，表模式 52.4–52.6（+16%）。两种模式每 25 s 切换的 A/B 会让刚切进来的模式
  重新预热，低估表模式（同时测出 48.6）；以后报稳态数字。
- PM4 包时间线（scratchpad patch_pm4trace.py 临时补丁 + pk_phase2.py，已还原）：表模式把阶段 4（主批翻译）从 15.5
  缩到 12.75 ms；阶段 2（帧标签 -> 主批提交）两种模式都约 7 ms：上一帧主批的 GPU 尾巴 4.8 ms（帧标签写入时还有
  41–46 个命令缓冲没完成，GPU 这段时间一直忙），然后才轮到下一帧的剔除 GPU 工作和回读。游戏在帧标签前等 GPU
  空闲，所以剔除不能和尾巴并行。
- GPU 屏障：每帧约 2440 个，46% 来自 UploadDirtyRanges（每次上传前后各一个 AllCommands 屏障），17% 来自
  Buffer::CopyFrom。去掉上传/拷贝前的全排空（不安全，只测上界）：同进程 47.8/47.8/47.5 vs 48.0/47.9/47.9，
  GPU busy 不变——不是瓶颈。
- 下一步：GPU 时间本身（5090 上每帧约 14 ms）。tracem 标记里单次的全屏计算 pass 0.3–0.7 ms（0x2088d0a00、
  0x208950600、0x20894d500 ...），剔除着色器 0x208ac7300 每帧 316 次。

## 3.13 Valley 转身的 GPU 冻结（10-05 早晨）

- 现象：世界巡检 wt3/wt4 里 Valley（world-valley）转身时有 0.9–1.2 s 的帧（native 没有）；单独复现（scratchpad
  valley-spin.ps1：每 100 ms 采样各线程 CPU 时间和 nvidia-smi 的 GPU 占用）：走完一圈后的第一次转身 0.7–2.6 s 的帧，
  GPU 占用 87–100%，渲染线程在等游戏（游戏在等 GPU），有时 TDR（VK_ERROR_DEVICE_LOST）；后面的转身正常 = 首次使用。
- 定位：tracem（GPU 时间戳）把时间记在了一个屏障上（屏障前有没打标记的工作）；带追踪时冻结超过 2 s 直接 TDR，拿不到
  数据。改用开关二分：只开表绘制干净，只开表派发冻结；Valley 独有的 137 个表派发程序全部退回普通路径就干净；二分发现
  两半里都有会冻结的程序（大量粒子类 CS：34 槽位/5 缓冲/写 3 个，100–140 槽位/12 缓冲/写 7 个）——是系统性问题。
- 原因：TableBlocks 每解析一个缓冲就把它的设备地址写进块里；后面的某次 ObtainBuffer 注册了缓冲（与已有缓冲合并时
  旧缓冲被换掉），前面写进块里的地址就指向了旧缓冲。新特效第一次出现时它的缓冲还没注册，正好触发。普通路径在所有
  查找之后才按最终的缓冲重新绑定（RebindBuffers）。粒子模拟读到的计数、链表就成了另一个缓冲里的内容，GPU 跑飞。
- 修正：表绘制/表派发在 TableBlocks 前记下缓冲注册纪元，所有查找（参数、索引、间接派发参数）之后纪元变了就交给
  普通路径（table_registered 计数；下一次使用时缓冲已注册）；写入的缓冲先解析，同一范围的只读 V# 随后看到它已归 GPU
  （与普通路径第二遍查找一致，不再读环形缓冲里的客体字节副本）。Valley 3 次转身 57.4/60.2/60.2 fps，最长帧
  69.8/19.9/19.8 ms（修正前每次 34 fps 左右、1–2.6 s 的帧）。
- 同时修了：表路径的直接绘制（DRAW_INDEX_2/OFFSET_2）用的是存储时那次绘制的顶点偏移/起始实例，而它们来自每次绘制
  的 user data（取顶点偏移、实例偏移的 SGPR）；改为每次绘制按 ResolveVertexOffset/ResolveInstanceOffset 的规则计算
  （变体只记顶点程序是否自带取顶点）。TryNativeDirectDraw 也打 GPU 标记了（以前 tracem 里直接绘制没有标记）。

## 3.14 预热与表模式管线缓存（10-05 上午）

- 用户关注帧率稳定（1% low）。13 世界对比：站立/转身表模式多数持平或更好，行走（新内容进视野）和进新区域后的
  一段时间更差。1-1 HUD 后每 10 s：表模式 43.5、49.9、52.0–52.3，native 一直 44.5–45.1；1-2：表模式 42.7、47.2、
  48.6、56.7、59+，native 47.2–48.3。预热期的表模式比 native 还慢。
- 编译任务计时（临时 TABLETIME 行，scratchpad tabletime.py）：1-2 预热期 table 计算管线约 650 个，每个 0.7–4 s
  （最长 16.6 s），共约 640 s CPU，11 个后台线程上近一分钟；图形管线 371 个平均 105 ms，表模式翻译 1651 个平均
  11 ms。原因：静态预编译里没有表模式管线；驱动管线缓存只在窗口正常退出时保存（测试都是结束进程，表模式管线
  从未存下），而且主缓存过 1 GiB 就整个重来（760 MB 加上表模式管线就会超过）。
- 改：表模式管线用自己的驱动缓存（_PipelineCache/local/<key>/<title>.table.bin，2 GiB 上限），表模式编译停下
  20 s 后由后台线程（Kyty.TableCache）保存，退出时也保存；加载/保存的代码与主缓存共用（LoadDriverCache /
  SaveDriverCache）。表模式翻译的着色器模块在编译线程上创建（渲染线程只发布）。
- 结果（1-2 连续两次启动）：第一次（缓存空）42.8、44.6、45.3、53.6、55；保存 66 MB；第二次 HUD 后第一个 10 s
  就是 56.7（native 47.2），之后 55.5–56.1，没有预热期。
